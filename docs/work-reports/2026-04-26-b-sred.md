## SR&ED Project 1: Empirical Reverse-Engineering of Closed-Source Page-Builder DOM Structures for Programmatic Content Migration

*Mapped from: Task 3 in work report 2026-04-26-b.md*

### 1. Technological Uncertainty (Form T661, Line 242)

**Existing knowledge base:**
The team operates a Next.js 16 web application requiring migration of a 24-post WordPress blog into the new MDX-driven editorial template. The source site is built on the Elementor page builder, a closed-source SaaS that emits its own non-standard widget-tree DOM structure (no `<article>` element, no semantic `<main>` wrapper, no consistent class hierarchy across post templates). Standard HTML-to-Markdown migration tools (Pandoc, Turndown applied to the full document) and standard scraping tools (Firecrawl, Puppeteer + Mozilla Readability) all rely on detecting a meaningful semantic content boundary. None of these tools have published recipes for extracting clean article bodies from Elementor-generated WordPress sites, and the structure differs not only between site templates but also between individual posts within the same site (some posts use Elementor's `theme-post-content` widget; this site uses a custom mix of `text-editor.default`, `heading.default`, `image.default`, and `icon-list.default` widgets in arbitrary order).

**Technological uncertainty:**
It was not known how to programmatically distinguish the article body from the rest of the page (header, navbar, footer, sidebar, related-posts grids, share buttons, lead forms, comment sections) for an Elementor-rendered post when (a) there is no semantic `<article>` boundary, (b) heading levels are inconsistently used (some posts have the title as `<h1>`, others as `<h2>`, others embed it inside an Elementor heading widget with class `elementor-heading-title`), (c) the same selector that captures the title region also captures all sibling sections including the sidebar (because the page-level Elementor wrapper contains everything), and (d) the SEO-customized `og:title` metadata diverges from the on-page heading text (Rank Math/Yoast plugins allow editors to set OG titles independently), defeating substring-match strategies.

**Why standard practice was insufficient:**
Multiple established techniques were attempted and discarded:
- **Mozilla Readability** (the algorithm behind Firefox Reader View): produces empty output on Elementor pages because it expects either a single dominant content `<div>` or a clear `<article>` element; Elementor distributes body across many sibling widget divs with no shared parent.
- **Firecrawl with `onlyMainContent: true`**: returns the markdown but mixes navbar, body, and sidebar in document order with no demarcation. Manual cleanup per post would have required ~6 hours of human attention.
- **Naive `closest(".elementor-section")` ancestor traversal**: matches the page-level wrapper because Elementor nests every section inside an outer `.elementor` container.
- **`og:title` substring matching against on-page headings**: failed for 9 of 23 posts where the SEO-customized OG title diverged from the page H2.
- **Heading-level (`<h1>`) detection**: failed because Elementor renders article titles as `<h2>` for SEO/style reasons.

### 2. Systematic Investigation (Form T661, Line 244)

**Hypothesis/Approach:**
We hypothesized that Elementor's underlying widget metadata (`data-widget_type` and `data-element_type` attributes on every widget) could serve as a semantic boundary that the rendered HTML's standard tag/class structure does not. Specifically: (1) a consistent set of widget types (`text-editor.default`, `heading.default`, `image.default`, `icon-list.default`, `image-box.default`) constitute body content across all posts, while non-body widgets (`mega-menu.default`, `breadcrumbs.default`, `posts.classic`, `posts.cards`, `share-buttons.default`, `social-icons.default`, `form.default`, `theme-site-logo.default`, `button.default`) constitute chrome and can be excluded; (2) the article body is the contiguous run of body widgets in document order between the title heading and the "Categories" sidebar heading; (3) the article title itself can be reliably identified as the first `.elementor-heading-title` element in document order, regardless of OG title customization, because sidebar headings always come later in the DOM.

**Work performed:**
1. **Iteration 1 — `closest(".elementor-section")` strategy.** Identified the title element via `<h1>` matching, walked up to the closest section, and returned the section's full subtree. Result: ~10/23 posts returned exactly 1,482-character output (just the navbar HTML), confirming the navbar's section was matching `.closest()`. Hypothesis discarded.

2. **Iteration 2 — TreeWalker with widget filtering.** Used `document.createTreeWalker(doc.body, NodeFilter.SHOW_ELEMENT)` to traverse all elements in document order. Gated collection on `started = true` after passing the title element. Filter passed only nodes with `data-widget_type` matching the body whitelist. Termination condition: `node === categoriesEl || categoriesEl.contains(node) || node.contains(categoriesEl)`. Result: zero collection. Diagnosed via instrumented walker: `node.contains(categoriesEl)` matches `<body>` (because body contains everything), firing the break before the title was even visited. Hypothesis refined.

3. **Iteration 3 — Removed ancestor-contains check.** Changed termination to `started && node === categoriesEl`. Title detection still used og:title prefix-match. Result: 14/23 posts succeeded with substantial bodies (5KB-28KB), 9/23 returned 278 characters. Diagnosed via post-by-post comparison: the 9 failing posts had OG titles intentionally differing from on-page H2s (verified by inspecting raw HTML — the Rank Math SEO plugin allows decoupling these). Hypothesis refined: title detection cannot depend on OG title.

4. **Iteration 4 — First-heading-in-document-order strategy.** Replaced the prefix-match with `headings[0]` (the first `.elementor-heading-title` in DOM order). Verified empirically that across all 23 posts, the article title is always the first such element (sidebar headings — Categories, Recent Posts, More Related Content, Subscribe, Follow Us — appear after it in the document). Result: 23/23 posts succeeded with body sizes 5KB-41KB.

5. **Markdown post-processing pipeline.** Designed cleanup regex stack: strip `## Categories`-onwards (sidebar bleed-through), demote body-level `# H1` to `## H2` (since the page title is rendered by `HeroCover` from frontmatter, not the body), strip `### by BRIO Team` byline headings, strip date-only paragraph lines (`/^[A-Z][a-z]+ \d{1,2}, \d{4}$/`), strip "Image Source:" attribution orphans (left behind after base64-stripped images), convert internal absolute URLs to relative paths (`https://builtbybrio.com/X` → `/X`), strip trailing slashes from internal links, collapse 3+ blank lines to 2.

6. **Cover image extraction.** Determined that `og:image:secure_url` is more reliable than `og:image` and far more reliable than the JSON-extracted "first image in body" — the latter routinely returned the BRIO logo PNG instead of the article cover. Image extension preserved from URL (`.webp` / `.jpg` / `.png` / `.jpeg`).

- 23 generated MDX files in `content/blog/`

### 3. Technological Advancement (Form T661, Line 246)

**Advancement achieved:**
- Established a generalizable extraction pattern for Elementor-built WordPress sites: walk the DOM via `TreeWalker`, gate on the first `.elementor-heading-title` element, collect only widgets matching a body-content whitelist of `data-widget_type` values, terminate on the "Categories" sidebar heading (or any other identifiable sidebar marker). This pattern is applicable to any Elementor site without site-specific selector tuning.
- Determined that on-page heading text is more reliable than `og:title` metadata for identifying article boundaries in Elementor sites where SEO plugins decouple the two — a finding not documented in any current Firecrawl, Mozilla Readability, or Puppeteer tutorial.
- Demonstrated that the `data-widget_type` attribute (Elementor's internal metadata exposed to the rendered DOM) can substitute for the missing semantic HTML5 elements (`<article>`, `<main>`, `<aside>`) when migrating closed-source page-builder content to open formats.
- Validated a Markdown post-processing pipeline tailored to WordPress blog idioms (BRIO Team byline patterns, date-only lines, base64-stripped image orphans, absolute-to-relative link normalization) that produces clean enough output to publish without per-post hand-editing.

**Residual uncertainty:**
- Unknown whether the same widget-walker pattern works on Elementor sites that use the `theme-post-content` widget (which encapsulates the full body in a single Elementor wrapper). Brio's site does NOT use this widget; future migrations of other Elementor sites may require detection logic that switches strategies based on widget presence. Deferred until a second site needs migration.
- Some inline images present on the live site were base64-stripped during scraping and are now orphaned in the migrated content (the script removes the orphan lines but does not download replacement assets). Manual addition per post is required if the visual content is needed.

## SR&ED Project 2: Diagnostic Investigation of Undocumented MDX Frontmatter Rendering Behavior in Next.js 16

*Mapped from: Task 5 in work report 2026-04-26-b.md*

### 1. Technological Uncertainty (Form T661, Line 242)

**Existing knowledge base:**
The team uses `@next/mdx` (the official Next.js MDX integration) combined with `gray-matter` (the de-facto YAML frontmatter parser for the JavaScript ecosystem) to render MDX-based blog posts. The standard pattern across Next.js MDX tutorials, the Vercel Portfolio Starter Kit, and the official Next.js docs example is to use `gray-matter` to extract frontmatter for data-layer access (`getPostBySlug`, etc.) while letting `@next/mdx` handle MDX rendering. Frontmatter-aware behavior — meaning the `---...---` block at the top of a `.mdx` file is excluded from the rendered output — is the user's natural expectation because (a) Markdown ecosystem tools (VuePress, Docusaurus, Astro, Gatsby) handle frontmatter transparently by default, (b) the popular `next-mdx-remote` package handles it transparently, and (c) the visible part of the Next.js MDX docs example does not require any frontmatter-handling configuration.

**Technological uncertainty:**
It was not known why every migrated blog post was rendering its YAML frontmatter as a giant bold/serif/underlined heading at the top of the body. Build succeeded, type-check passed, `gray-matter`-based metadata access worked correctly, and the basement-suite proof-of-concept post had previously rendered correctly — yet the symptom appeared on all 25 posts after deployment. The visual signature was specific and unusual: the entire YAML key:value block (title, slug, date, tags, coverImage URL, alt text, excerpt) appeared as one contiguous large heading in the article font, wrapped in what looked like a hyperlink. Standard MDX troubleshooting (checking JSX vs MDX file extension, mdx-components.tsx component overrides, gray-matter parsing) returned no anomalies.

**Why standard practice was insufficient:**
Standard MDX integration patterns assume one of three frontmatter strategies: (a) use only `gray-matter` and import the MDX body as a string, parsing it through a separate runtime renderer; (b) use `next-mdx-remote` which has built-in frontmatter handling; or (c) use a starter template like Vercel Portfolio Starter that pre-configures frontmatter handling. The team's setup does not match any of these — it uses `@next/mdx`'s file-import pattern (`await import('@/content/blog/${slug}.mdx')`) with `gray-matter` only for metadata access. The interaction between these two — specifically what `@next/mdx` does with the leading `---` block when no frontmatter plugin is configured — is undocumented in any tutorial or Stack Overflow answer the team could find.

### 2. Systematic Investigation (Form T661, Line 244)

**Hypothesis/Approach:**
We hypothesized that the visual signature (large serif heading + underline + entire YAML block as one element) was consistent with Markdown's setext H2 syntax (`text\n---` becomes `<h2>text</h2>`), which would imply that `@next/mdx` was treating the closing `---` of the frontmatter as a setext heading underline rather than as a frontmatter delimiter, and that all the YAML lines between the two `---` separators were being collapsed into a paragraph that then became the H2's text content. The autolink-headings rehype plugin (configured with `behavior: "wrap"`) would then wrap that fake H2 in an `<a>` tag, producing the underline.

**Work performed:**
1. **Visual signature analysis.** User provided screenshot showing the rendered output. Observed: bold + serif font (matches our `mdx-components.tsx` H2 styling: `font-heading text-brio-navy text-[26px] md:text-[30px] font-semibold mt-12 mb-4`), underline (matches our `mdx-components.tsx` `<a>` element styling: `underline underline-offset-2`), all on one element (the entire YAML block as one heading). Hypothesis: the closing `---` is being interpreted as a setext H2 underline.

2. **MDX spec verification.** Reviewed the CommonMark spec section on setext headings: any non-blank text followed by `---` on the next line becomes an H2. The leading `---` of frontmatter is a thematic break (`<hr>`) when not preceded by content.

3. **`@next/mdx` documentation review.** Re-read `node_modules/next/dist/docs/01-app/02-guides/mdx.md`, specifically the "Frontmatter" section: explicit statement "@next/mdx does NOT support frontmatter by default" with a list of recommended remark plugins (`remark-frontmatter`, `remark-mdx-frontmatter`, `gray-matter`). The hypothesis was confirmed: without `remark-frontmatter`, `@next/mdx` does treat `---` as Markdown.

4. **Verification of basement-suite post.** Confirmed via spot-check that the basement-suite proof-of-concept post (manually written before the migration script) suffered the same bug — the user simply had not noticed because they had only spot-checked the welcome post (which has shorter frontmatter and similar serif styling that may have visually blended).

5. **Fix application and verification.** Installed `remark-frontmatter`, added it as the FIRST plugin in `next.config.ts` `remarkPlugins` array (before `remark-gfm` so it processes the YAML block before any other transformation). Cleared `.next` cache. Rebuilt. Verified all 25 posts now render hero-then-body correctly.

**Evidence artifacts:**
- Commit: `60cec8f` (brio-website)
- File: `next.config.ts` (1-line change to `remarkPlugins` array)
- User screenshot artifact (showing the bug)
- `node_modules/next/dist/docs/01-app/02-guides/mdx.md` (Next.js docs reference)
- Long-lived feedback memory: `~/.claude/projects/-Users-amirsmacbookair-claude/memory/feedback_next_mdx_frontmatter.md`

### 3. Technological Advancement (Form T661, Line 246)

**Advancement achieved:**
- Established the externally-observable visual signature of the `@next/mdx` frontmatter-as-content failure mode (large serif H2 wrapped in autolink anchor at the top of every post) so that future occurrences can be diagnosed in seconds rather than from scratch.
- Documented the precise interaction between `gray-matter` (used independently for data access) and `@next/mdx` (which treats the file as Markdown), clarifying that adding `remark-frontmatter` to `@next/mdx` does NOT conflict with `gray-matter` use elsewhere — they are independent layers.
- Determined that the order of remark plugins matters: `remark-frontmatter` must precede `remark-gfm` (or any other transformer) so the YAML block is recognized and excluded before downstream plugins parse the content tree.
- Validated that `behavior: "wrap"` on `rehype-autolink-headings` interacts with the bug to produce the underlined-link visual signature, helping future debuggers recognize the bug from the symptom.

**Residual uncertainty:**
- It is unknown whether `@next/mdx` has any other implicit Markdown-vs-frontmatter ambiguity edge cases (e.g., `---` appearing mid-document, indented frontmatter, frontmatter with embedded `---`) that could produce similar mis-rendering. The team has not stress-tested these scenarios; they are deferred until they appear in real content.

## SR&ED Project 3: Design and Validation of a Multi-Variant Editorial Blog Template Architecture for a Service-Business Conversion Funnel

*Mapped from: Task 1 in work report 2026-04-26-b.md*

### 1. Technological Uncertainty (Form T661, Line 242)

**Existing knowledge base:**
The team has 14+ landing pages and a city-page layout that all use a shared compact `LeadForm` component for end-of-page lead capture. The blog rebuild needed to introduce a NEW lead-capture pattern (mid-article inline form + topic-matched end-of-article form) without breaking the existing form contract or duplicating its 100+ lines of validation, GHL payload assembly, or implicit-SMS-consent disclaimer logic. Additionally, the editorial template needed to support per-article configuration of which service-bucket the end-of-article CTA targets (kitchen post → "Get My Free Kitchen Estimate", basement post → "Get My Free Basement Estimate", etc.) without per-page hardcoding or component duplication.

**Technological uncertainty:**
It was not known whether a single shared `LeadForm` component could be cleanly reused inside MDX-rendered blog posts with three distinct presentation contexts (compact inline mid-article, stacked end-of-article in a navy reverse-out section, and the existing landing-page contexts) while (a) preserving its existing `source` / `service` / `submitLabel` prop API for existing callers, (b) automatically prefixing the `source` for blog-context attribution in GHL (so analytics can distinguish blog-inline submissions from landing-page submissions), (c) topic-matching the headline + submit label per-service via a service-keyed lookup table, and (d) keeping the implicit-consent SMS pattern (no checkbox, disclaimer adjacent to submit button) consistent across all three contexts.

**Why standard practice was insufficient:**
Standard React component composition patterns (children-prop wrappers, render-prop callbacks, headless components + presentational shells) all require either (a) refactoring `LeadForm` to expose internal state — which would break the 14+ existing callers and require changing their props — or (b) duplicating `LeadForm` logic into a `BlogLeadForm` variant — which would duplicate the GHL payload assembly, validation, and consent disclaimer that just had a critical bug fixed earlier in the day. Neither was acceptable.

### 2. Systematic Investigation (Form T661, Line 244)

**Hypothesis/Approach:**
We hypothesized that the existing `LeadForm` component's `variant` prop (which already supports `"stacked"` vs `"compact"`) plus its `source` prop could serve as the integration boundary. By wrapping `LeadForm` in two thin presentational components — `InlineLeadForm` (mid-article, compact variant, source auto-prefixed `blog-inline-{slug}`) and `EndOfArticleCTA` (end-of-article, stacked variant, source auto-prefixed `blog-end-{slug}`, headline/subhead/submitLabel looked up from a service-keyed table) — we could provide three distinct presentations without modifying `LeadForm` at all.

**Work performed:**
1. **Designed `InlineLeadForm`** as a compact mid-article aside: navy-bordered box with headline + dek + LeadForm (compact variant) + auto-prefixed source. Headline/subhead defaults provided but overridable per insertion.

2. **Designed `EndOfArticleCTA`** with a service-keyed lookup table mapping each service slug to a custom headline/subhead/submitLabel triple. Service slugs not in the table fall back to a generic "general" entry. Wrapping is a navy reverse-out section with `id="blog-end"` so the meta-strip's "Jump to estimate ↓" anchor link works.

3. **Verified backward compatibility** by inspecting all 14+ existing `<LeadForm />` callers across `app/{service}/page.tsx` files and `components/city/CityPageLayout.tsx`. Confirmed that none of the existing prop API was changed and no callers needed updating.

4. **Validated the source-prefix pattern** ensures blog-context lead attribution in GHL by tracing the payload assembly: `LeadForm` props pass `source` through to `lib/ghl.ts`'s `submitLead`, which assembles tags like `src-{source}` so blog-attributed leads will appear with `src-blog-inline-{slug}` or `src-blog-end-{slug}` tags in GHL — distinguishable from `src-{landing-page-slug}` for landing page submissions.

5. **Designed the in-MDX exposure** through `mdx-components.tsx`'s `useMDXComponents()` return object. Custom components (`CalloutCard`, `PullQuote`, `Figure`, `BeforeAfterSlider`, `InlineLeadForm`) become directly usable inside `.mdx` files without explicit imports. This enables content authors (or the migration script) to drop in `<InlineLeadForm source="my-post-slug" />` mid-article without React knowledge.

**Evidence artifacts:**
- Commit: `297dbee` (brio-website)
- Files: `components/blog/InlineLeadForm.tsx`, `components/blog/EndOfArticleCTA.tsx`, `mdx-components.tsx`, `app/blog/[slug]/page.tsx`, `lib/blog.ts`
- Verification: backward compatibility confirmed via grep of `<LeadForm` usages — zero callers changed

### 3. Technological Advancement (Form T661, Line 246)

**Advancement achieved:**
- Established a reusable architectural pattern for shared form components that need to operate in editorial-content contexts: thin presentational wrappers that pre-configure props (`variant`, `source` prefix, service-keyed copy) without modifying the underlying form. This pattern is generalizable beyond blogs to any future content surface that needs lead capture.
- Validated that GHL's tag-based attribution model (consumed downstream by Workflow #1's Service Router and Workflow #9's urgency/financing tagger) supports per-context source prefixing without GHL workflow changes — the `src-blog-inline-*` and `src-blog-end-*` tags arrive in the contact's tag list and can be filtered by smart lists or workflow conditions.
- Demonstrated that MDX's component-injection pattern (via `useMDXComponents()`) cleanly solves the "content authors should not need React knowledge" problem for inline lead-capture and other interactive elements, without requiring a custom MDX runtime.

**Residual uncertainty:**
- The conversion-rate uplift of mid-article inline forms vs end-of-article-only forms in the trades-industry context is not known. The decision to include both was based on best-practice research (Stripe Press, Linear blog, Descript patterns) but Brio's own conversion data has not yet been measured. A/B testing deferred until ad traffic is flowing.
